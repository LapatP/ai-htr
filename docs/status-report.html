Project status · ai-htr

Reading blood pressure off hospital OPD cards

The cropping half of the pipeline is built and measured. The reading half does not work, and the thing blocking it is paper, not code.

Prepared 26 August 2026 Scope v1 — blood pressure, 4 form templates Runs entirely offline
Summary where things stand

The system takes a scanned or photographed hospital outpatient card and pulls the blood pressure out of it, in two halves: find and crop the field on the page, then read the handwriting inside it. Everything runs on a single local machine, because the eventual inputs are patient records.

Stages 0 through 3 — everything up to and including the crop — are built and measured. Stage 4, the reader, is wired end to end but is not usable: it turns a real 143/90 into 111/10. No machine-learning model has been trained or downloaded at any point; the current reader is a template-matching baseline with zero learned parameters, which is precisely why it fails.

Evidence what has been measured

Cropping holds up under degradation

With one real scan per form, comparing a page against a template built from that same page measures nothing. So robustness is tested by synthetic perturbation: warp a page by a transform we chose, add the damage a phone camera adds, and ask the pipeline to recover it. Because the transform is known, the ground truth is exact.

The measure is coverage, not overlap. A crop that clips a digit has failed however good its overlap score; extra whitespace costs nothing. That choice is clinical, not aesthetic — a clipped leading digit turns 143 into 43.

Coverage is flat from clean to heavy. Registration error is sub-pixel — mean 0.35 px against a BP field roughly 175 × 73 px. Of the five heavy-degradation failures, all five were refusals and none was a misidentification: the system reported "unknown form" rather than cropping against a guess. That asymmetry is deliberate and is the single most important property of the design.

Problem stage 4

The reader does not work, and it knows too little to know it

The current reader compares each handwritten glyph against 198 templates rendered from a vector font library. On the one genuinely filled BP field available, it reads two of six characters correctly. The three digits it gets wrong — 4, 3 and 9 — all collapse to the same answer, 1.

The confidence figure is therefore not merely imprecise, it is uninformative: every score sits in a narrow band around 0.55–0.75 regardless of whether the answer is right, so there is no threshold that separates good readings from bad ones.

Worth separating clearly, because it changes what needs fixing: the segmentation is already correct. On real degraded handwriting the system isolates all six characters in the right places. Only the final classification step fails. That narrows the problem considerably.

New this week

A test set built from real ink

To test the cropping properly, the pipeline needs pages where the handwriting sits in a known but awkward position. Rendering numbers in a font would not do — the reader's own templates come from those same fonts, so any score measured that way grades the system against its own answer sheet.

Instead the generator harvests the real pen strokes already on the card and recomposes them into new values. Reviewing the source page turned up more genuine handwritten digits than expected: the triage sticker's vitals block carries temperature, pulse, respiratory rate and oxygen saturation alongside the blood pressure. That yields real ink for seven of the ten digits.

From these, the generator produces pages carrying arbitrary plausible readings, with the value displaced from its box, the page tilted and warped, and the triage sticker itself relocated — all with exact ground truth. Digits 5, 7 and 8 do not appear anywhere on the source page and remain untested.

What that immediately found

Two defects that the previous test data could not have surfaced, both in code that had already been measured as working.

1 · Crop refinement cannot follow ink downward

The crop box grows sideways to catch a value written wide, but will not grow down to catch one written low. Splitting the same twelve pages by which way the handwriting moved:

The same twelve pages, split by direction
Handwriting movedPagesMean coverageWorst
Up, or level999.0%95.2%

Sideways displacement of up to 80 px is absorbed without difficulty. A downward displacement of 39 px removes two thirds of the value from the crop.

2 · A missed field is not treated as a disagreement

On the worst page above, the pipeline did not report a bad reading. It reported no reading at all — it marked the field empty. The page carries a blood pressure of 160/102.

Why this one matters more than a wrong number

The design's central safety property is that the base card and the triage sticker record the same visit twice, so the two readings can be cross-checked against each other with no reference data at all. On this page the sticker was read correctly at full coverage.

But the cross-check compares readings that exist. With the base card contributing nothing, only one reading remained, and one reading is treated as "nothing to cross-check" — so the page passed as plausible. An absent field currently counts as no information, rather than as a contradiction with a source that does have a value. A wrong number would have been caught. A missing one was not.

Both defects are fixable and neither is deep. The point worth taking is that the existing measurements did not reveal them, and a test set built from real ink did so within a day.

Constraint read before trusting any accuracy figure

Every source page currently available has been through messaging-app compression and arrives at roughly 103 dpi. The document-scanning standard is 300 dpi and optical character recognition generally wants 200 as a floor. At 103 dpi a handwritten 143/90 occupies about 60 × 25 px, and 8 pt printed Thai is around 11 px tall — effectively unreadable.

This does not affect the cropping stages, which have ample features to work with at that resolution. It caps the reader, and the digits in a vitals block are exactly the highest-stakes characters on the page.

Internally the system already works at 300 dpi, so better scans need no configuration changes when they arrive.

Request what would unblock this

The bottleneck is paper, not engineering

Three genuinely filled blood-pressure fields exist in the entire corpus, and all three are on the same card, in one person's handwriting, recording the same measurement. No reader — template-based, trained, or commercial — can be honestly evaluated against that. Reporting an accuracy figure from a single example would be meaningless, and the project has deliberately not done so.

  1. 1

    20–30 filled OPD cards

    The binding constraint. Enough distinct handwriting to measure a reader at all, and to establish whether errors cluster by writer, by pen, or by field. Fully de-identified is fine — only the vitals block is needed.

  2. 2

    One blank base OPD card

    Dissolves three separate problems at once. The current template is a filled page with a sticker attached to it, which forces the system to work around content that is not part of the form. A clean blank would remove that compromise from template matching, field registration, and the crop-refinement constants together.

  3. 3

    Scans at 300 dpi

    A flatbed or department scanner rather than a phone photograph forwarded through a messaging app. This costs nothing and roughly triples the pixels on every digit.

Caveats stated plainly
  • Every figure in this report is synthetic. Nothing has been tested against a second real scan of any form.
  • One writer. All harvested handwriting comes from a single person on a single page, so it shows nothing about variation between writers.
  • Digits 5, 7 and 8 are untested — they do not appear on the source page.
  • Only one field archetype is implemented. Checkboxes, circled Y/N tokens and grid cells are declared but unmeasured. Diagram fields are deferred as a research problem.
  • The degradation levels in the newest test set are not directly comparable to one another, because displacement was drawn at random rather than held fixed across them. The up-versus-down split above is unaffected by this.
