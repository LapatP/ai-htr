ai-htr — blood pressure off hospital OPD cards

Scan an outpatient card → find the BP field → crop it → read it as two integers.
Runs entirely on one machine. No internet, no GPU, and no ML model anywhere — because the real inputs are patient records.

Short version: cropping works and is measured ✅, reading does not work ❌, and the thing actually blocking it is paper, not code.

Worth separating clearly 📖

Segmentation already works. On real, degraded handwriting it isolates all six characters in the correct places. Only the final classification step fails. That narrows the problem a great deal.

New this week test set built from real ink

Built a new test generator that does not render digits with a font — the reader's own templates come from those same fonts, so scoring against them is grading the system on its own answer sheet. Instead it harvests the real pen strokes already on the card and recomposes them into new values.

Looking properly turned up more real handwriting than expected: the triage sticker's vitals block carries T 36.9, P 64, R 20 and O2 Sat 96 alongside BP 143/90. That's genuine ink for 7 of the 10 digits — enough to compose arbitrary BP values, displace them from their box, tilt the page and move the sticker, all with exact ground truth.

Digits 5, 7 and 8 appear nowhere on the page, so they remain untested.

Sideways displacement of 80 px is absorbed comfortably. Downward displacement of just 39 px loses two thirds of the value. Every case below 95% is one written lower — no exceptions.

2 · A missing field isn't counted as a disagreement

On the worst page above, the system didn't report a wrong value. It reported the field as empty (field_empty) — on a page carrying a blood pressure of 160/102.

The safeguard here is that the card and the sticker record the same visit twice, so the two can be cross-checked with no reference data at all. The sticker was read correctly. But the check only compares readings that exist — with the card contributing nothing, one reading was left, and one reading is treated as "nothing to cross-check". It passed clean.

A wrong number gets caught. A missing one doesn't. An absent field currently counts as no information, rather than as a contradiction with a source that does have a value.

Neither defect is deep and both are fixable. The point is that the existing measurements never surfaced them, and a test set built from real ink found both within a day.

Resolution ceiling — read before trusting any accuracy figure

Every source page so far has been through messaging-app compression and arrives at about 103 dpi. The document scanning standard is 300, and OCR generally wants 200 as a floor.

At 103 dpi a handwritten 143/90 is roughly 60×25 px, and 8 pt printed Thai is around 11 px tall — unreadable more or less by construction. This does not affect cropping, which has ample features to work with, but it is a hard ceiling on the reader. Internally the system already works at 300 dpi, so better scans need no config changes whatsoever.

The ask — this is a paper problem, not an engineering one

The entire corpus contains 3 filled BP fields, all on the same card, in one person's handwriting, recording the same measurement. No reader — hand-built, trained, or bought — can be honestly evaluated on that. Quoting an accuracy figure from a single example would be meaningless, so this project deliberately hasn't.

1
20–30 filled OPD cards

The binding constraint. Enough distinct handwriting to measure a reader at all, and to see whether errors cluster by writer, by pen, or by field. Fully de-identified is fine — only the vital signs block is needed.

2
One blank OPD card

Solves three problems at once. The template is currently a filled card with a sticker attached, so the system has to work around content that isn't part of the form. A blank one would clear template matching, registration, and the tuned refinement constants together.

3
Scans at 300 dpi

A department scanner instead of a phone photo forwarded through a chat app. Costs nothing and roughly triples the pixels on every digit.

Limitations, stated plainly

  • Every number in this report is from synthetic data. Nothing has been tested against a second real scan of any form.
  • One writer. All harvested ink comes from one person on one page, so it says nothing about variation between writers.
  • Digits 5, 7 and 8 are untested — they don't exist on the source page.
  • Only one field type is finished — a value written on a ruled line. Checkboxes, circled Y/N and grid cells are declared but unmeasured.
  • The damage levels in the new test set aren't directly comparable to each other, because displacement was drawn at random rather than held fixed. The up-versus-down split above is unaffected by this.
